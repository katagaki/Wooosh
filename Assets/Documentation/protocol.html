Protocol Version 1

How Wooosh Moves A File

Wooosh is local-network file sharing for Android, iOS, macOS, and Windows. There are no accounts, no cloud, and no server anyone has to run. Two devices find each other on the same Wi-Fi network, open an encrypted QUIC connection directly to one another, prove who they are with pinned public keys, and stream files that are hash-verified before they are ever placed where you can see them. This page walks through the two flows that matter: a transfer between strangers, and a transfer between devices that have been paired.

01What Wooosh Is

Everything below is drawn from the normative specification. The wire details come from the Wooosh Protocol Specification, and the product behaviour comes from the Wooosh System Design document.

Three facts shape every diagram on this page.

  • Identity is a key, not an account. Each install generates one Ed25519 identity keypair on first launch and stores the private half in the platform keystore. The DeviceID a user sees is BLAKE3(pubkey)[0..16], rendered as four base32 groups and as a six-word fingerprint phrase.
  • Trust is pinning, not certificate authorities. Every connection is QUIC with TLS 1.3 and mutual certificates, but the certificate is only an envelope around the Ed25519 identity key. CA chains are never evaluated. The verification callback is the pinning logic.
  • Discovery carries no identity. The mDNS advertisement contains a rotating discovery ID that is not derived from the identity key. The long-term public key is deliberately absent from the broadcast, so a passive listener cannot follow a device from one network to the next.
Reading The Diagrams

Both diagrams are vertical sequence diagrams. Each device owns one dashed vertical lifeline, and time runs downward. The narrow coloured rail down the left edge shows the security state of the channel at that moment in time, and it changes only where the protocol changes it.

02Legend

Solid Blue Arrow
A protocol message sent inside the encrypted QUIC connection, on the bidirectional control stream or a file stream. The head points at the receiver.
Dashed Blue Arrow
A discovery announcement on the local network: multicast mDNS, or the UDP 44777 fallback. Not part of any connection.
Dashed Grey Arrow
Something that happens outside the network: a camera reading a QR code, or two people comparing what is on their screens.
Boxed Note On A Lifeline
Work one device does on its own: a validation rule, a consent decision, hash verification, or a write to the trust store.
No Channel
Nothing is connected yet, or the connection has closed. Only discovery traffic exists at this point.
Untrusted
TLS 1.3 is up and the traffic is encrypted, but the peer is not authenticated. Only HELLO, pairing messages, and (in Everyone mode) OFFER are honoured.
Trusted
The peer presented a public key that is pinned in this device's trust store. The channel is encrypted and authenticated.
Rejected
A hard failure with a typed close code, such as QR_KEY_MISMATCH, TOKEN_INVALID, or KEY_CHANGED.
Close Codes Are The Contract

A QUIC close() discards buffered stream data, so a rejection frame written just before closing usually never arrives. The application close code is the only reliable rejection signal, and the connecting side must map it to a typed error. "This device only accepts paired senders" and "the network dropped" call for very different responses from the person holding the phone.

03Scenario One: Alice Sends To Bob, Unpaired

Alice has never met Bob. Bob is running in Everyone mode, which means Wooosh announces him on the network and lets unpaired senders make an offer, subject to consent. The channel is encrypted from the first packet after the QUIC Initial, but it stays untrusted for the whole exchange unless Bob chooses to pair.

Figure 1 Unpaired Transfer In Everyone Mode Scroll sideways if the diagram is wider than your window

Why The Channel Never Turns Green Here

Bob chose Accept Once, so nothing was written to his trust store. The connection was encrypted end to end for its whole life, and the two people verified each other by eye, but the next time Alice appears on the network Bob will see her as an unknown device again and will be asked again. That is the correct behaviour for a one-off transfer at a conference table.

Had Bob tapped Pair and Accept, Alice's public key would have been pinned, and the next connection would open in the trusted state shown in Scenario Two.

Everyone Mode Is Rate Limited

Unpaired offers are limited to three per minute per rotating ID and source, with an auto-mute option, so a device in a crowded room cannot be used to spam offer sheets. Paired Only mode rejects unpaired senders at the handshake instead, before any offer is possible.

04Scenario Two: Carol And Dylon Pair By QR

Carol wants Dylon's device to be a device she keeps. She displays a QR code; Dylon scans it. The scan delivers Carol's public key over a channel no network attacker can touch, which is exactly what makes the ceremony resistant to a man in the middle. After pairing, every later transfer between them authenticates silently.

05The Two Verification Ceremonies

First contact is the only moment a man in the middle has a chance. Wooosh closes it in one of two ways, and both work by making the attacker's substituted key visible to a person rather than only to software.

QR Code · Out-Of-Band Key Delivery

The receiver shows wooosh-pair:1?pk=…&tok=…&dn=…&hints=…&exp=… on screen. The sender's camera reads it, so the public key arrives over light, not over the network.

An attacker who controls the whole Wi-Fi network can still forward, drop, or replay packets. What the attacker cannot do is get their own key into the sender's hands, because the sender already holds the real one and compares the presented certificate key against it. A mismatch aborts with QR_KEY_MISMATCH before anything else happens.

The 32-byte token in the same payload closes the other direction: it proves the connecting device really scanned the code, which is both proximity and authorisation. It is single use, expires after 120 seconds, and is compared in constant time.

Six-Digit Code · Short Authentication String

Where there is no camera, either side can send PAIR_REQUEST {} with no token over the untrusted channel, and both devices compute the same number from the TLS session itself.

SAS = BE_u32(HKDF(exporter, "wooosh-sas-v1")[0..4]) mod 1_000_000

Here exporter is the 32-byte TLS 1.3 exporter secret, taken under the label EXPORTER-wooosh-sas.

The exporter secret binds both certificates and the entire handshake transcript. An active man in the middle has to terminate two separate TLS sessions, one with each side, and cannot force the two derived numbers to agree. Guessing a match is a one in a million proposition. Both users confirm, PAIR_CONFIRM flows both ways, and the keys are stored. Any mismatch, or 60 seconds of silence, aborts without storing anything.

A Third Artifact, Easy To Confuse

The six-word fingerprint phrase in Figure 1 is not the six-digit code. The phrase is a rendering of a peer's own long-term identity key and is shown on the consent sheet for an unpaired sender, so it reads the same on both devices no matter which connection is open. The six-digit code is derived from one specific TLS session and is meaningless outside it. Shells never reimplement either one: both come out of the core through fingerprint_phrase_for(pubkey) and the SAS event.

06Details Worth Keeping In View

Discovery Is A Hint, Never A Decision

The TXT record and the UDP 44777 fallback datagram carry the same fields, and listeners de-duplicate by rotating ID. Everything in them is untrusted material for populating a list. The v value is only a pre-filter; real version negotiation happens inside the encrypted HELLO, which is what stops a spoofed TXT record from forcing a downgrade. The device type value tells the receiving list which glyph to draw, and an unrecognised or missing value must render as a neutral glyph. A generic icon is always acceptable. A confidently wrong one is not.

Verification Comes Before Placement, Always

Received bytes land in staging/<tid>/<fid>.part, preallocated to the offered size. A file is only moved to the Photos library, to Downloads, or into the Files app after its BLAKE3 hash matches the value in the manifest. A transfer is never reported complete for a file the recipient cannot find, name collisions append a counter rather than overwriting, and staging older than seven days is collected automatically.

The Resume Ledger Is An Optimisation

The receiver keeps a small record of verified offsets so an interrupted transfer can pick up where it stopped. Authority always rests with the bytes on disk plus the BLAKE3 result, so a ledger read or write failure is logged and swallowed. Failing a slot stream over a ledger error would strand every file queued behind it, and the transfer could never finish. The worst case for a lost ledger update is re-hashing part of a file on the next resume.
